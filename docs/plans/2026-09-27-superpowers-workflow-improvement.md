## 1. 테스트 실행을 감독하는 단일 실행기 — P0

구현자·리뷰어·컨트롤러는 모두 같은 실행기를 사용한다. 보고서 파일 유무만으로 기다리지 않는다.
단일 진입점은 `scripts/run_tests.py`로 한다. 내부 책임은 다음처럼 나눈다.

| 구성 요소 | 책임 |
|---|---|
| CLI | 인자 검증, 입력 fingerprint, worktree 실행 잠금, 감독 프로세스 시작, 결과 표시 |
| 감독 프로세스 | pytest 시작·시간 감시·진단 요청·종료·잔류 확인·최종 결과의 유일한 작성자 |
| 독립 pytest plugin | collection 및 setup/call/teardown 시작·종료 이벤트, 수집된 nodeid와 결과 기록 |

감독 프로세스와 pytest는 각각 별도 세션으로 시작한다. CLI 종료로 감독 프로세스가 함께
사라지지 않게 하고, CLI 전용 제어 파이프의 EOF 또는 취소 요청을 감독 프로세스가 감지하면
해당 pytest 프로세스 그룹을 회수한다. 파이프 쓰기 끝은 pytest/Chromium에 상속하지 않는다.
소유권 이전과 실행 재접속은 초기 구현에서 지원하지 않는다. 소유 CLI가 사라지면 취소한다.
감독 프로세스가 그룹 식별자를 확보하기 전에 pytest가 테스트를 시작하지 않도록 시작 handshake를 둔다.

독립 plugin은 `-p`로 명시적으로 로드해 프로젝트 `conftest.py` 수집보다 먼저 준비한다.
pytest hook의 시작 이벤트는 동작 **전에**, 종료 이벤트는 동작 후에 기록한다.
완료 report만 수집해서는 멈춘 setup을 볼 수 없다. plugin 준비 전 멈춤도 startup 예산으로 종료한다.
hook 계약은 [pytest 공식 API](https://docs.pytest.org/en/stable/reference/reference.html#pytest.hookspec.pytest_runtest_protocol)를 따른다.

기록할 항목: run_id, task_id, agent_id, 코드 상태, 명령, 시작 시각, PID/프로세스 그룹,
현재 nodeid, setup/call/teardown 단계, 마지막 단계 전환 시각, 종료 코드, 로그/진단 경로.
추가 항목: schema_version, 정책 버전, worker_id(초기값 master), event sequence,
테스트 시작 시각, 단계 시작 시각, 전체 마감, effective timeout, 종료 사유, cleanup 결과.
경과 시간과 마감에는 monotonic clock, 사람이 읽는 기록에는 UTC를 사용한다.
plugin은 append-only 이벤트를 쓰고 감독 프로세스만 상태·결과 파일을 원자적으로 교체한다.
잘린 마지막 이벤트는 무시하되 이벤트 손실·역순은 증거 불완전으로 기록한다.
결과 파일이 없어도 프로세스 종료를 감지하며, 불완전한 실행을 성공으로 추정하지 않는다.

초기 시간 정책(실측 후 조정할 제안값):

| 항목 | 초기값 | 동작 |
|---|---:|---|
| 감독 프로세스 감시 주기 | 최대 1초 | 프로세스·제어 채널·시간 예산 확인 |
| 에이전트의 상태 확인 | 30초 | 진행 내용을 읽어 보고. 이 주기가 실제 종료를 제어하지 않음 |
| startup | 30초 | pytest spawn부터 plugin 준비까지 |
| collection | 60초 | plugin 준비부터 수집·실행 준비 완료까지 |
| 동일 테스트/단계 장기 체류 | 60초 | 둘 중 먼저 도달한 기준으로 진단 요청, slow 표시 |
| 테스트 1개 protocol 전체 | 120초 | protocol 시작 이벤트부터 누적. setup/call/teardown과 protocol 종료까지 포함 |
| 테스트 사이의 무이벤트 간격 | 30초 | 이전 테스트 종료부터 다음 시작까지 |
| 최종 정리 | 30초 | 마지막 테스트 종료 또는 수집 실패부터 pytest 프로세스 종료까지 |
| 일반 전체 스위트 | 600초 | pytest spawn부터 종료까지. 개별 예외가 있어도 자동 연장하지 않음 |
| 종료 유예 | 10초 | SIGTERM 후 SIGKILL까지. 진단도 이 시간 안에서만 수행 |
| 강제 종료 후 잔류 확인 | 5초 | 종료를 확인하지 못해도 무한 대기하지 않고 cleanup 실패 기록 |

heartbeat는 실행기가 살아 있다는 증거일 뿐 테스트가 진행 중이라는 증거가 아니다.
로그 증가도 진척으로 간주하지 않는다. 현재 테스트의 경과 시간과 단계 전환을 따로 감시한다.
적용 중인 전체·단계·테스트 마감 중 가장 빠른 것이 우선한다. 테스트와 단계 slow 진단은
각각 한 번만 남기고 정상 예외의 진단 기준은 해당 예외 예산 안에서 지정한다.
collection 완료 후에는 collection 마감을 해제한다. 수집 실패/0개 수집도 최종 정리 감시로 전환한다.
외부 감독이 모든 hard deadline과 TIMED_OUT 판정을 단독 소유한다.
독립 plugin은 `pytest_runtest_protocol`의 시작/종료 시각을 monotonic 값으로 기록하고 즉시 flush한다.
감독은 수신 시각이 아니라 이벤트의 시작 시각으로 테스트 마감을 계산한다.
시작 이벤트가 오기 전에는 startup/collection/inter-test/전체 마감을 유지한다.
예외는 독립 plugin의 `runner_timeout(seconds, reason)` marker로 지정하고 수집 단계에서 검증한다.
유한한 양수와 사유가 필요하며, 전체 예산을 넘으면 테스트 실행 전에 오류 처리한다.
기본 정책과 유효한 marker 이외의 timeout 덮어쓰기는 지원하지 않는다.

P0에는 pytest-timeout을 추가하지 않는다. 이미 설치돼 있어도 이 실행에서는 로드를 제외하고,
기존 timeout marker·CLI·환경/설정이 발견되면 조용히 무시하지 않고 지원 계약 불일치로 보고한다.
무제한 예산, func_only, xdist도 지원하지 않는다. 독립 plugin은 관측만 하고 종료 timer를 만들지 않는다.
faulthandler는 진단만 담당한다. 이렇게 하면 내부 timer가 코드 1로 먼저 종료해 일반 실패와
혼동되는 경합을 없앨 수 있다. 이 문제는 [pytest-timeout 공식 구현](https://github.com/pytest-dev/pytest-timeout/blob/main/pytest_timeout.py)의
protocol timer와 `os._exit(1)` 경로를 검토해 확인했다.
강제 종료 시 teardown/JUnit 결과가 없을 수 있으므로 외부 상태·원래 종료 코드·진행 이벤트로 판정한다.

60초 진단은 준비 handshake에서 등록을 확인한 pytest 프로세스에만 신호를 보낸다.
Python thread stack은 [faulthandler.register](https://docs.python.org/3/library/faulthandler.html#faulthandler.register)로
전용 파일에 기록한다. 등록 전에는 신호를 보내지 않는다. 스택이나 Playwright trace가 없으면
그 사유를 남기며 종료는 계속한다. Python 스택을 Chromium 내부 스택으로 해석하지 않는다.
스택/trace는 선택적 진단이다. 이 산출물만 실패해도 `diagnostic_status`와 사유를 기록하되,
필수 실행 증거가 완전하면 PASSED와 결과 재사용을 허용한다. timeout 등 기존 실패 사유도 바꾸지 않는다.
출력은 파일로 직접 흘려보내고 제한된 tail만 읽는다. PIPE를 비우지 않아 자식이 막히는 구조와
진단용 subprocess의 제한 없는 대기를 피한다.
[Python subprocess 문서](https://docs.python.org/3/library/subprocess.html)의 세션 생성·PIPE 주의사항을 따른다.

종료 코드를 받았어도 해당 그룹에 자식이 남으면 회수한다. 테스트 중 관측한 자식은 PID와
생성 시각을 함께 기록하고, 그룹을 벗어난 자식에 신호를 보낼 때도 소유권을 재확인한다.
PID만 적힌 과거 파일을 근거로 kill하지 않는다. 전체 시스템의 pytest/브라우저를 일괄 종료하지 않는다.
프로세스 트리 식별에 필요한 라이브러리(예: psutil)는 개발 의존성으로 선언하고 해당 API를 검증한다.

감독 프로세스 자체의 SIGKILL, OS 중단, 관측 전에 그룹을 벗어난 자식까지 완전 회수한다고
보장하지 않는다. 다음 실행은 이전 nonterminal run의 프로세스 신원을 확인해 `INTERRUPTED`로
복구하고, 확인 가능한 잔류만 정리한다. 신원이나 정리 여부가 불확실하면 잠금을 강제 해제하지 않고
충돌 실행을 거부하며 진단을 남긴다. 상시 외부 감시 서비스는 초기 범위 밖이다.
내부 timer를 제거했으므로 감독 프로세스의 강제 사망 후 pytest를 독립적으로 종료할 백업도 없다.
이 상황은 정상 감독하의 유한 deadline 보장과 구분해 다음 실행 복구 대상으로 유지한다.
따라서 "무한 대기 0건"은 지원하는 장애 주입 시나리오의 수용 목표로 한정한다.

수명주기는 `STARTING → RUNNING → STOPPING → FINISHED`로 고정한다.
자연 종료도 잔류 확인을 위해 STOPPING을 거친다. `slow`와 `diagnostic_requested`는 부가 속성이다.
최종 outcome은 `PASSED / FAILED / TIMED_OUT / CANCELLED / INFRA_ERROR / INTERRUPTED` 중 하나다.
마감 위반을 기록한 뒤 자식이 0으로 종료해도 TIMED_OUT을 유지한다. cleanup 실패는
원래 종료 사유와 별도로 보존하며 PASSED 판정을 금지한다.
pytest의 원래 종료 코드와 signal은 별도 필드에 보존한다. CLI 반환 코드는 정상 pytest 종료는
그 코드를 유지하고 timeout=124, 인프라/정리 실패=125, 취소=130으로 한다.
pytest 코드 5(0개 수집)는 성공 증거로 쓰지 않는다. 중단 복구는 상태 확인 명령에서 125로 보고한다.

같은 명령을 원인 분석 없이 반복하지 않는다. 실패 nodeid만 재현하고 fixture/락/종료 순서를 조사한다.
nodeid가 없는 collection/startup 실패는 마지막 모듈·plugin·단계로 최소 재현 범위를 정한다.

### 산출물과 진입점 계약

다음 인터페이스는 구현되어 있다. 설치와 지원 경계는 [사용 문서](../test-runner.md)를 따른다.

```text
python scripts/run_tests.py --task-id T1 --agent-id implementer -- tests/test_gimpo_jobs.py -q
python scripts/run_tests.py --task-id FINAL --agent-id controller -- -q
python scripts/run_tests.py --status <run_id>
```

결과는 worktree별 `.test-runs/<run_id>/`에 `manifest.json`, `events.jsonl`, `status.json`,
`result.json`, `stdout.log`, `stderr.log`, `stacks.log`로 보존한다. `.test-runs/`는 gitignore 대상이다.
프로젝트의 SDD 임시 workspace와 분리해 SDD 정리 후에도 증거가 남게 한다.
같은 worktree의 중복 실행은 PID 파일 존재 여부가 아니라 OS 잠금으로 막는다.
CLI 사망 시에도 감독 프로세스가 정리 완료까지 실행 잠금을 유지한다.
상태 조회는 잠금 없이 가능하며, 자동 결과 재사용 캐시는 초기 구현에서 만들지 않는다.
다른 에이전트는 run_id를 인용해 기존 증거를 확인한다.
환경은 실행에 영향을 주는 허용 목록과 버전만 기록하고 비밀값·전체 환경 덤프는 저장하지 않는다.
비밀 입력이 결과에 영향을 주면 통제된 테스트 값으로 대체하거나 재사용 불가로 표시한다.

완료 기준: setup, 본문, teardown, collection의 의도적 멈춤과 자식 프로세스 잔류를 각각
주입해 제한 시간 내 비정상 종료·진단 보존·고아 프로세스 정리가 되는지 검증한다.
빠른 정상 실행과 정상적인 장기 실행 예외도 검증한다.
구체적인 장애 주입 행렬은 아래 실행 과제와 함께 고정한다.

## 2. 검증 범위와 증거 재사용 — P1

| 변경 단계 | 필요한 검증 |
|---|---|
| 구현 중 | 실패 재현 테스트와 직접 영향받는 테스트 |
| 과제 완료 | 현재 SDD implementer template에 따라 과제 커밋 전 전체 스위트 1회. 수용 조건도 대조 |
| 수정 라운드 | 지적 재현 + 수정 영향 범위 회귀 테스트 |
| 변경 없는 리뷰 | 구현자의 증거 확인. 같은 테스트 재실행 금지 |
| 최종 통합 | 최종 코드 상태에서 전체 스위트 1회 성공 |

conftest, 공용 fixture, 공용 JS/CSS, 의존성, 전역 상태 등 영향 범위가 넓거나 불명확하면
중간에도 전체 검증을 허용하고 사유를 기록한다. 전체 스위트 1회는 최종 상태에 대한 원칙이며
실패 이후 재검증을 금지하는 횟수 제한이 아니다. 최종 코드가 바뀌면 증거 유효성을 재판정한다.
기존 안의 "과제 완료도 영향 범위만, 전체는 최종에만"은 현재 implementer template과 다르다.
이를 단순한 SDD 준수로 포장하지 않는다. 범위 축소는 별도의 명시적 워크플로우 변경 제안으로 남긴다.
현행 finishing 스킬은 전체 스위트를 새로 실행하도록 한다. 마지막 과제 커밋 후 코드가 바뀌지
않았어도 과제 완료의 전체 검증과 중복될 수 있으며, 배치 순서만으로 이를 제거할 수 없다.
플러그인 계약을 변경하기 전에는 finishing 재실행을 `required-by-finishing` 사유의 잔여 중복으로 기록한다.
계약 변경 후의 목표는 finishing에서 동일 최종 fingerprint의 유효한 전체 검증 증거를 재사용하고,
증거가 없거나 코드·환경이 바뀌었으면 실행하는 것이다. 현재 가능한 동작과 이 목표를 구분한다.
전역 직접 재검증과 verification 스킬의 모호성은 지침 감사의 I-01/I-06에서 먼저 정리한다.

결과에는 commit뿐 아니라 미커밋/미추적 입력을 포함한 코드 상태, 테스트 목록, 명령·환경·의존성,
시각, 종료 코드, 성공/실패/건너뜀 개수, 로그 경로를 남긴다.
동일 코드·환경·범위의 성공만 재사용한다. 환경 변화나 flaky 정황이 있으면 재실행 사유를 기록한다.
단순히 HEAD가 같다는 이유로 수정 전 테스트를 재사용하지 않는다.

입력 manifest는 경로·파일 내용 해시·삭제·파일 모드·심볼릭 링크 대상을 포함한다.
tracked 파일과 gitignore에 걸리지 않는 untracked 파일, 실제 읽는 ignored 설정/fixture를 포함하고,
생성 로그·캐시·`.test-runs`만 제외한다. 제외 입력이 실행에 영향을 주면 재사용을 거부한다.
환경 fingerprint에는 Python 실행 경로/버전, 실제 설치된 패키지와 plugin 버전, OS/아키텍처,
Playwright 브라우저 revision, 허용한 테스트 환경값, 실행기/plugin/정책 버전을 포함한다.
requirements.txt만 같은 것은 같은 환경이 아니다. 테스트 목록은 선택 인자뿐 아니라 수집 nodeid도 남긴다.

실행 전후 manifest를 비교하고 변경되면 `reusable=false`로 한다. 전후 해시 일치는 실행 도중
수정했다 복원한 경우를 검출하지 못하므로, 같은 worktree에서 실행 중 입력을 쓰지 않는 계약도 필요하다.
초기 구현은 협조적 쓰기 중지를 전제로 한다. 강한 증명이 필요한 동시 작업은 별도 스냅샷에서 검증한다.
PASSED, cleanup 성공, 입력 불변, 결과/로그 완전, 수용 조건에 필요한 테스트 실행을 모두 확인해야
재사용한다. skip/xfail은 자동 승인하지 않고 해당 수용 조건과 대조한다. 단위 테스트 통과로
통합 동작을 대체하거나 서로 다른 fingerprint의 부분 성공을 전체 성공처럼 합치지 않는다.

pytest --durations로 느린 테스트를 식별한 뒤 순차 실행 기준을 확보한다.
pytest-xdist는 파일·DB·포트·환경변수·전역 자원 격리를 확인하고 2 workers부터 비교한다.
처음부터 -n auto를 적용하지 않는다. 브라우저 메모리와 경합 때문에 병렬화가 악화될 수도 있다.
worker별 진행 이벤트를 수집해 한 worker의 출력이 다른 worker의 멈춤을 가리지 않게 한다.
xdist 적용은 반복 측정에서 시간 개선과 안정성이 확인된 범위만 채택한다.

## 3. 리뷰 비용을 줄이는 운영 — P1

아래 SDD 절차는 설계 이해를 위한 요약이다. AGENTS.md/CLAUDE.md에 복사할 규칙 목록이 아니다.
과제별 brief에는 제품 수용 조건과 프로젝트 테스트 명령만 전달하고 기존 reviewer template을 사용한다.

구현 → 과제 리뷰 1회(요구 충족 + 품질 두 판정) → 필요한 수정과 범위 재리뷰 → 최종 통합 리뷰.
동일 diff에 별도의 중복 리뷰어를 붙이지 않는다. 구현자는 리뷰 에이전트를 추가 생성하지 않는다.
작업량보다 리뷰 준비가 더 큰 초소형 과제는 설계 단계에서 같은 수용 조건 단위로 묶는다.

- 최초 계획 점검에서 의존성, 파일 소유권, 공용 인터페이스, 수용 조건을 표로 추출한다.
  이후에는 이 표와 변경된 계획 부분을 점검하며 전체 3,600행을 반복 대조하지 않는다.
  5분이 지나면 발견 내용과 미해결 사항을 기록하고 조사 범위를 좁힌다. 시간 초과를 승인으로 처리하지 않는다.
- 과제 리뷰 입력은 brief, BASE..HEAD diff, 테스트 증거, 구속력 있는 요구사항이다.
  BASE는 dispatch 직전에 기록한다. 미커밋/미추적 구현이 있으면 이를 포함한 스냅샷 diff와
  파일 목록을 추가한다. 리뷰 입력 fingerprint와 검증 결과가 다르면 먼저 증거를 맞춘다.
- 재리뷰는 기존 finding ID의 해결 여부와 수정 diff가 만든 회귀만 확인한다.
- Minor는 기록하되 수정 루프를 열지 않는다. 제목이 Minor라도 실제 요구 위반이면 근거로 재분류한다.
- 같은 지적이 2회 해결되지 않으면 접근법·재현 조건을 재검토한다. 이것은 조기 진단 신호이며
  기존 SDD의 최대 5회 루프/판정 절차를 임의로 축소하거나 결함을 통과시키는 규칙이 아니다.
- 최종 리뷰 수정은 한 묶음, 재리뷰 1회다. 남은 항목은 판단 근거와 영향을 기록한다.
  미해결 핵심 결함을 시간 예산 때문에 완료 처리하지 않는다.
  루프 종료와 제품 수용 조건 충족을 구분해 잔여 핵심 결함이 있으면 미완료로 보고한다.
  새로운 실패를 숨겨 통과시키거나 임의로 두 번째 최종 수정 루프를 만들지 않는다.

이전 세션은 Codex 기본 effort를 high로 변경했다고 보고했다. 이번 리뷰에서 설정을 변경하지 않는다.
모델·effort는 역할 시작 시 확정하고 같은 수정 담당을 재개할 때 유지한다. 매 dispatch마다
임의로 재선택하지 않는다. 최종 리뷰·난항 시 승격은 품질상 이유로 유지하되 캐시 비용도 기록한다.
정의 파일과 호출 인자를 동시에 정본으로 두지 않는다. 모델 인자를 제거하는 훅은 캐시 최적화의
근거가 아니며, 요청값/훅 적용값/실제 usage 모델의 일치 여부를 따로 검증한다.
동일 기본값의 명시와 설정 변경은 구분한다. 공급자 API의 캐시 보존 기능을 Claude Code/Codex
서브에이전트 도구가 노출한다고 가정하지 않는다. 세부 측정·판정은 지침 감사의 캐시 절을 따른다.

## 4. 후속 작업의 범위 고정 — P1

"미룬 문제 모두 해결"을 시작할 때 기존 finding ID 목록과 수용 조건을 고정한다.
완료 조건은 그 목록의 해결이다. 실행 중 새 Minor가 생겨도 현재 목록에 자동 편입하지 않는다.
새 Critical/Important 회귀나 기존 수용 조건 실패는 현재 작업에 포함하고 추가 사유를 남긴다.
그 밖의 발견은 별도 backlog로 보존하고 최종 결과에 공개한다.

### T1 장애 주입 수용 행렬

| 시나리오 | 기대 결과 |
|---|---|
| 정상 통과/실패/skip/0개 수집 | 원래 pytest 코드와 개수 보존. skip 또는 0개를 수용 조건 통과로 오인하지 않음 |
| plugin 로드 전·collection·setup·본문·teardown·최종 정리 멈춤 | 해당 예산으로 종료, 마지막 확인 단계와 진단 가능 여부 보존 |
| setup/call/teardown이 각각 50초 | 단계별로 120초를 새로 주지 않고 protocol 누적 120초에 중단 |
| protocol 시작 뒤 setup 전에 멈춤, 시작 이벤트 누락 | 전자는 테스트 마감, 후자는 유지 중인 상위 마감으로 종료. stderr 추정 없이 TIMED_OUT 판정 |
| 출력만 계속 증가하는 멈춤 | 로그 증가로 마감 연장 없음 |
| 자식이 SIGTERM 무시 또는 pytest만 먼저 종료 | SIGKILL/잔류 확인 유예 안에서 처리, 다른 실행의 브라우저는 유지 |
| CLI 취소·강제 종료 | 감독 프로세스가 제어 채널 종료를 확인하고 pytest 회수 |
| 감독 프로세스 강제 종료·오래된 PID 상태 | 다음 실행에서 신원 확인 후 복구. 불확실한 프로세스를 종료하지 않음 |
| 필수 이벤트·로그·결과 파일 손실 | 성공/재사용 금지. INFRA_ERROR 또는 기존 timeout 사유를 보존하고 증거 손실 기록 |
| 스택/trace 확보만 실패 후 테스트 정상 종료 | 진단 실패 사유 보존. 필수 증거가 완전하면 PASSED/재사용 허용 |
| 유한한 장기 실행 예외 | 수집 시 검증한 예산이 감독의 단일 마감에 반영됨. 전체 마감을 암묵적으로 늘리지 않음 |
| 실행 중 입력 변경·중복 실행 요청 | 결과 재사용 금지 또는 잠금 충돌 반환 |

장애 검사는 작은 임시 pytest 프로젝트로 수행해 업무 테스트에 의도적 hang을 넣지 않는다.
빠른 검사에는 비율을 유지한 축소 시간 정책을 사용하고 기본 60/120초 정책도 대표 1건 확인한다.
감독 기능을 검증하는 검사에는 검사 대상과 독립적인 외부 유한 deadline을 둔다.

플러그인 캐시 파일은 직접 수정하지 않는다. 현재 지침과 호환되는 저장소 운영 규칙부터 적용한다.
플러그인 자체 변경이 필요해지면 별도 관리 가능한 소스에서 개발한다.
이하 정책은 r3 설계 기준이다. 이후 구현 및 검증의 범위는 [구현 기록](2026-09-27-superpowers-workflow-implementation.md)에서 구분한다.

## 측정 및 채택 기준

- 초기 목표: 멈춤 진단 60초에 요청, 일반 테스트 120초에 종료 시작.
  지원 장애에서 감시 오차 1초 + 종료 유예 10초 + 잔류 확인 5초 안에 결과 확정.
  진단 요청 시각과 실제 스택 확보 시각은 별도 측정한다. OS가 실행기를 스케줄하지 못하는 상황은 보장 밖이다.
- 동일 코드·환경·범위의 사유 없는 전체 스위트 중복 0회.
  현행 finishing 의무에 따른 중복은 별도로 집계하며 0회 달성으로 숨기지 않는다.
- Minor만으로 열린 추가 수정 라운드 0회, 범위 밖 항목의 자동 편입 0건.
- 구현/테스트/리뷰/대기를 구분한 실제 wall-clock, 테스트 worker 시간, 수정 라운드 수,
  flaky 실패, 뒤늦게 발견한 회귀를 기록한다. 병렬 시간들을 단순 합산하지 않는다.
- 캐시는 전체와 각 에이전트 첫 호출을 분리해 읽기·생성·미캐시 입력과 출력 토큰을 기록한다.
  높은 적중률만으로 채택하지 않고 총 입력량·실제 소요 시간·재작업·품질을 함께 평가한다.
- 속도 개선은 시범 과제에서 측정한다. 회귀나 flaky 증가가 나타나면 해당 최적화는 되돌린다.
  현재 수치만으로 전체 소요 시간의 절감률을 보장하지 않는다.
