## 사용자가 추가로 확정한 규칙

일반 설정은 `config/gimpo_parking.toml`에서 T2와 같은 공용 로더로 읽고 엄격히 검증한다. 텔레그램은 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ALARM_ENABLED`(기본 false)를 모든 서비스가 공유한다. 프로젝트 루트 `.env`에서 공통 설정을 읽고 실행 환경의 값을 우선한다. 서비스 접두사가 붙은 텔레그램 설정은 사용하지 않는다.

객체의 책임은 구성(`GimpoService`), 작업 수명(`GimpoRuntime`), 저장(`JobStore`), 공식 화면(`PlaywrightGimpoClient`), 전달(`NotificationOutbox`, `TelegramNotifier`)로 나눴다. `BrowserClient`·`Notifier` Protocol과 생성자 주입으로 외부 연동을 대체한다. GoF 패턴을 개수에 맞춰 도입하지 않고 어댑터와 생성 책임 분리 등 필요한 구조를 선택했다. 별도의 상태별 클래스 상속 계층은 만들지 않았다.

## 검증 근거

| 수용 항목 | 로컬 검증 |
|---|---|
| R1 | 실제 Chromium fixture에서 누적 핸들러·더블클릭·다른 탭·취소 직후 재진입. 허용된 payment.json 전달은 최초 1회 이하 |
| R2 | 동일 SQLite 트랜잭션으로 중지와 전송 경합. 결제 전송/진행/결과 불명에서 수정·중지·새 작업 거부 |
| R3 | 결제 모달 취소·숨김·페이지 이탈·브라우저 닫힘. 결제 이후 모달 숨김을 취소로 처리하지 않음 |
| R4 | 기한 경과와 정확한 경계의 전송 거부, 새 generation 재준비, 만차·세션 오류 때 READY 미생성 |
| R5 | OS 잠금, debug/reloader 거부, 구성 객체의 지연 워커 시작, 종료·복구 상태 |
| R6 | 실제 자체 화면에서 입력→결제 대기→새로고침→동일 작업 재연결→중지. 비밀번호 미복원, 알림 중복 생성 없음 |
| R7 | 재시도 대기 중 인계 취소·만료·결제 시작·중지·세션 종료. 전송 중 상태 변경의 정정 1회 생성 |
| R8 | SENT/전송 중 종료 복구, SENDING→UNKNOWN, 브라우저 없는 정정, 반복 복구 중복 억제 |
| R9 | 타임아웃 UNKNOWN, 명시적 재발송 회차 중복 거부, 인증 오류·재시도 소진 분류 |
| R10 | 서버 45일·30일 경계·입력 형식·10분 단위. Chromium 서울·뉴욕(DST)·호놀룰루 시간대에서 같은 달력 결과. T2 기본 옵션 유지 |
| R11 | 0/음수 보증금 및 직접 insertAction 차단. 정상 음수 receiptAmt 허용 |
| R12 | READY+outbox 저장 중 장애 롤백, 결제 시도 기록 실패 시 전송 불가, 기록 후 재시작 결과 불명 |
| R13 | HTTP 200 만차·오류 HTML, 중복/노쇼, 최종 만차의 준비 폐기, 일반 외 할인 거부 |
| R14 | 알림 실패 시 브라우저 유지, 상태/저장 DB에 비밀번호·연락처 미포함, 기본값의 비밀번호 제외, localStorage 미사용, 중지 후 응답 폐기 |

기본 테스트의 Python HTTP 전송은 전역 차단한다. 브라우저 fixture는 모든 응답을 로컬에서 제공하고 그 외 요청은 차단한다. 실제 공항에 대한 이번 세션 읽기는 시작 페이지 GET 및 공개 스크립트 확인뿐이며, 예약 생성·결제·실제 텔레그램 전송은 실행하지 않았다.

초기 공식 페이지 캡처와 로컬 fixture 검증은 현재 사이트의 전체 실연동 및 실제 예약 완료를 입증하지 않는다. UI와 README에서 이 한계를 구분하고, RESERVED 자동 판정은 활성화하지 않았다.

## 공통 텔레그램 확장

사용자 추가 요청으로 발송기·재시도 결정·메시지 형식을 T2와 김포가 공유한다. 공통 활성화 변수는 `TELEGRAM_ALARM_ENABLED`이며 기본 `false`다. 서비스별 활성화 변수와 김포 TOML의 활성화 키는 제거했다. 공통 재시도 정책은 `config/notifications.toml`로 이동했다.

T2의 기존 HTTP 200 성공 처리(감시 및 1회 호출)에 완료 알림을 연결했다. 감시는 중지한 뒤 별도 큐에 넣으며, 알림 실패·타임아웃이 예약 요청을 재실행하지 않는다. 메시지는 서비스·입출차·완료 감지 시각·작업번호만 포함하고 원본 API 응답과 개인정보를 전송하지 않는다. T2 큐는 메모리 기반이고 김포는 기존 SQLite outbox 복구를 유지한다.

사용자가 확정한 별도 설정 메뉴 시안을 `/settings/`에 구현했다. 기존 예약 화면에는 새 탭으로 열리는 설정 링크를 추가하고, 김포의 공통 알림 패널을 설정 화면으로 옮겼다. 김포 예약별 알림 결과와 재전송은 해당 예약 화면에서 처리한다.

설정 화면은 공통 봇·수신자 설정 안내, 전체 알림 상태, 서비스별 전송 상태와 테스트 결과를 표시한다. 환경변수 값은 노출하지 않으며 화면에서 변경하지 않는다. 알림이 꺼져 있어도 자격정보 설정 여부는 별도로 표시한다. 조회는 예약 런타임·DB·브라우저·전송 워커를 시작하지 않는다. 두 서비스의 테스트 알림은 `BackgroundNotifications`를 사용하며 진행 중인 테스트 요청을 중복 등록하지 않는다. 김포의 실제 예약 알림은 기존 SQLite outbox를 유지한다.

### 코드 리뷰 후 보완

- 상태 조회는 현재 작업 ID와 상태 버전을 확인해 오래된 응답을 무시한다. 새 작업과 같은 작업의 재시작 모두 지연 응답 Playwright 테스트로 검증한다.
- 최종 만차 재조회 후에는 이전 브라우저 정리를 마친 다음 조회 대기 상태로 전환한다. 느린 브라우저 종료 중 감시 루프가 작업을 종료하지 않는지 검증한다.
- 알림 재발송 상태와 기존 발송 가능 이력을 별도로 보존한다. 재발송 대기·재시도·실패·전송 중 취소와 실행 복구 시에도 정정 안내와 원본 메시지 참조를 유지한다.

설정 화면의 켜짐·꺼짐·미설정·조회 실패 상태, 테스트 전송 결과와 중복 요청, 비밀값 미노출, 예약 런타임 미실행, 모바일 화면을 로컬 대역으로 검증한다.
