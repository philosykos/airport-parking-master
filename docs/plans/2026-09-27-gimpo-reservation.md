# 김포공항 예약 기능 명세

버전: 0.3 · 2026-09-27 · 구현 및 사용자 설정 규칙 반영. 검증 기록: `2026-09-27-gimpo-implementation.md`.

실제 브라우저 자동 진행과 결제 대기 시 텔레그램 알림을 제공한다. 현재 PC에서 Flask와 화면 표시 브라우저를 실행하는 단일 사용자·단일 프로세스를 1차 지원 범위로 한다. 텔레그램은 알림 수단이며 다른 기기에 공항 세션을 이전하는 수단은 아니다.

## 목표와 완료 기준

서비스 첫 화면에서 김포공항을 선택하고, 자체 입력 폼에 공항·주차장·일시·할인·차량번호·연락처·예약 비밀번호를 입력해 정상 예약 절차를 진행한다. T2와 유사한 1회 조회, 감시 시작/중지, 상태·로그 표시를 제공한다. 사용자가 자동 진행을 시작하면 실제 브라우저가 결제 대기까지 진행하고 텔레그램으로 안내한다. 실제 결제는 사용자가 유지된 공식 브라우저에서 진행한다.

완료 기준은 입력 폼에서 시작한 정상 예약이 동일한 공항 사이트 세션으로 정보입력·중복검사·잔여석 재조회·결제 진행 확인까지 도달하고, 그 시점에 텔레그램 발송과 열린 브라우저 인계가 작동하는 것이다. 결제 대기는 공항 사이트의 “결제 하시겠습니까?” 모달이 실제로 표시된 상태로 정의한다. 사용자가 확인하기 전 payment.json을 자동 호출하지 않는다. 결제창 표시를 예약 완료로 처리하지 않는다. 예약 완료 판정은 공식 화면의 완료 상태와 예약번호 등 검증된 증거가 있을 때만 한다.

## 현재 코드와 조사 결과

- `app.py`는 Flask 앱과 랜딩 화면을 구성하고 `services/t2_valet.py`의 Blueprint를 등록한다.
- `/t2-valet/` 및 `/t2-valet/api/*`가 분리돼 있다. `templates/landing.html`의 김포 카드만 활성화하면 별도 화면을 연결할 수 있다.
- T2는 단일 POST와 HTTP 200 성공 판정을 사용한다. 김포는 여러 단계와 쿠키 세션이 필요하고 HTTP 200에서도 만차 `10`이 반환되므로 이 동작을 복제하지 않는다.
- 김포 정상 흐름은 `recheck.do → reservationCheck.json → resInsert.do → duplicateReservation.json → reservationCheck.json → 결제 확인창 → payment.json → PG`다.
- 직접 확인한 정상 예약 날짜는 2026-09-29 10:00~14:00이다. 가용성은 테스트 당시 결과이며 고정 테스트 데이터로 실서비스에서 반복 사용하지 않는다.
- 정상 결제 확인의 요청을 전송 전에 캡처했다. `payment.json`은 `reservationVO` 폼을 URL 인코딩해 POST한다. 실제 서버 응답 및 PG 연동 결과는 아직 검증하지 않았다.
- 날짜와 금액은 서버가 생성한 2단계 폼에 들어간다. 숨김 날짜만 수정하면 화면·확인 문구·요금과 달라진다. 자체 서비스는 입력 변경 시 기존 준비 상태를 폐기하고 올바른 날짜로 다시 준비한다.
- 공식 `payment()`는 호출할 때마다 `#confirmOk` click 핸들러를 추가한다. 오프라인 재현에서 첫 진입은 확인 1회당 요청 1개, 재진입은 요청 2개였다. 자체 API 잠금 외에 공식 브라우저의 요청 전송 제어가 필요하다.
- 예약내용 확인은 native `confirm()`이고 결제 확인은 Bootstrap DOM 모달 `#confirm`이다. 결제 대기를 미응답 Playwright `dialog`로 유지하지 않는다. `#confirmNo`의 취소는 모달만 닫으므로 별도 상태 관측이 필요하다.
- `paymentAmt <= 0`이면 모달 없이 `insertAction.do`로 직접 제출하는 분기가 있다. 현재 일반 예약은 보증금 10,000원이지만 자동화는 이 예외에서도 예약 생성 전에 멈춰야 한다.

## 화면

새 경로는 `/gimpo-parking/`, 제목은 “김포공항 국내선 예약주차장”으로 한다. 기존 CSS 토큰, 입력 스타일, 로그 패널과 날짜 선택기를 재사용한다. T2 전용 DOM과 전역 함수에 연결된 `app.js`, `enhancement.js`는 그대로 불러오지 않는다.

기존 날짜 선택기의 약 두 달 고정 상한을 옵션으로 바꾼다. `/options`가 서울 기준 현재 시각·정책 버전·입차 하한·출차 상한·최소/최대 기간·분 단위를 제공하고, 달력 렌더링·직접 입력·서버 검증에 동일하게 적용한다. 김포의 확인된 10분 단위, 최소 2시간 사용, 최대 30일, 출차일 45일 범위를 관리한다. 안내의 입차 2시간 전 기준과 기존 JS의 단순 미래 시각 검사가 다르므로 보수적인 입차 하한을 적용하고 연동 검증에서 확인한다. T2의 기존 날짜 기본값은 유지한다.

| 입력/표시 | 자체 필드 | 공항 사이트 대응 | 처리 |
|---|---|---|---|
| 공항 선택 | airportCode | parkingDivCd | 김포공항을 기본 선택. 표시명은 확인된 선택 목록에서 결정 |
| 주차장 선택 | parkingId | sectnId / 1단계 parkingNm | 공항별 실제 목록에서 선택. 이름과 코드의 일치 확인 |
| 입차·출차 | entryAt, exitAt | resInDttm, resOutDttm | 서울 시간, 10분 단위 입력, 전송 시 초 포함 |
| 차량번호 | carNumber | carNo | 공백 정규화, 김포 화면이 허용하는 형식 검증 |
| 휴대전화 | phone | mobile | 숫자로 정규화, 서버에서도 검증 |
| 예약 비밀번호·확인 | reservationPassword, passwordConfirmation | password / passwordCk | 현재 확인된 영숫자 4자리 이상 규칙과 일치 검사. 로그인 비밀번호와 구분 |
| 할인 구분 | discountSelection | discountCd 및 공식 조회 결과 | 일반 기본값. 할인 요청은 공식 자격 조회 결과로 확정 |
| 약관·개인정보·위치 확인 | agreements | agree01/03/04/05 | 해당 내용 확인과 사용자 직접 동의 |
| 조회 주기 | intervalSeconds | 서비스 내부 설정 | 기본 30초의 순차 조회, 오류 시 간격 증가 |
| 예상 주차요금·보증금 | 서버 반환 표시값 | calculateAmt, depositAmt, paymentAmt 등 | 읽기 전용. 사용자가 임의 금액을 입력하지 않음 |

사용자 흐름: 정보·약관 입력 → “가능 여부 조회” 또는 “결제 대기까지 자동 진행” → 실제 00 확인 → 동일한 브라우저에서 공식 폼 입력·중복/잔여석 재확인 → 결제 진행 확인 모달 표시 → 감시 중지·브라우저 유지·텔레그램 알림 → 사용자가 해당 브라우저에서 확인하고 직접 결제. 1회 조회 모드는 정보 확인까지만 수행한다. 자동 진행 중 날짜·주차장·할인 결과가 사용자 입력과 다르면 REVIEW_REQUIRED로 중단하고 자체 화면에 사유를 표시한다.

“정보 불러오기/저장”은 T2와 비슷하게 제공하되 저장 전에 사용자의 선택을 받는다. T2에서 공통 차량번호·연락처를 가져오는 동작은 명시적 버튼으로 제공한다. 이름·차종·색상·항공편 등 김포 절차에 불필요한 T2 필드는 요구하지 않는다.

| `services/gimpo_jobs.py` | 작업 상태, 감시 스케줄, 취소·동시 실행·중복 요청 제어 |

| `services/telegram_notifier.py` | Bot API 발송, 실패 분류·재시도, 민감정보 제외 |

| `static/js/gimpo_parking.js` | 김포 폼과 자체 API 통신, 화면 상태 관리 |
| `tests/test_gimpo_*.py` | 검증·상태 전이·라우트·민감정보·오류 시나리오 |

초기 어댑터는 실제 확인된 흐름을 재현하는 표준 Playwright의 화면 표시 브라우저를 사용한다. 작업마다 BrowserContext를 분리하고, 브라우저 객체는 전용 워커 이벤트 루프에서 생성·사용·정리한다. Flask 요청 스레드는 브라우저 객체를 직접 조작하지 않고 명령을 전달한다. 기존 T2 워커와는 상태·중지 이벤트·로그를 분리한다. 결제 대기에서는 조회 루프만 중단하고 워커·페이지·쿠키 세션을 유지한다. 대기 중에도 워커는 사용자 클릭·네트워크·취소·종료 사건을 처리한다. 알림 발송은 별도 큐다.

김포의 활성 예약 작업은 1개로 제한한다. 작업 상태·활성 슬롯·결제 시도 표시·알림 생성/취소를 SQLite 트랜잭션으로 일관되게 기록한다. 외부 요청 응답을 기다리는 동안 DB 잠금을 유지하지 않는다. 브라우저 객체와 비밀정보는 런타임 메모리에서 관리하며 다중 WSGI 프로세스 배포는 지원하지 않는다.

운영 실행은 `debug=False`, `use_reloader=False`로 하고 README의 지원 실행 명령과 일치시킨다. 현재 `app.run(debug=True)`를 유지한 채 김포 운영을 지원하지 않는다. 워커는 import/reloader 부모 프로세스에서 시작하지 않는다. 시작·종료 훅과 단일 실행 잠금을 두고 두 번째 프로세스의 김포 작업 시작을 거부한다. 개발용 reloader 환경에서는 실제 김포 자동 진행을 비활성화한다.

김포 작업의 설정·저장 데이터·로그는 T2와 분리한다. 예약 비밀번호, 세션 쿠키 및 PG 토큰은 JSON 기본값 파일·로그·브라우저 localStorage에 저장하지 않고 작업 메모리에만 보관한다. 자체 상태 조회 응답에도 제외한다. 브라우저 trace·네트워크 원문·스크린샷도 기본 비활성화 또는 마스킹한다. 종료된 작업의 비밀번호는 정리하고 재준비에 필요하면 다시 입력받는다. 결제 진행·결과 불명의 자원 정리는 아래 상태별 규칙을 따른다.

현재 `t2_valet.py`는 import 시 REQUEST_URL이 없으면 프로세스를 종료한다. 김포 단독 실행 지원이 필요하므로 T2 설정 검사를 T2 사용 시점의 명확한 오류로 옮기는 최소 변경을 검토하고, 기존 T2 설정 오류 테스트를 보강한다. 공항 통신에서 T2의 `verify=False` 설정을 재사용하지 않는다.

## 자체 API 초안

모든 엔드포인트는 `/gimpo-parking/api` 아래 둔다. 공항 API 경로/URL을 클라이언트가 임의 지정하는 범용 프록시는 만들지 않는다. 변경 명령은 입력 버전/generation을 확인하고 오래된 명령은 409로 거부한다. 오래 걸리는 명령은 명령 ID와 202를 반환하고 상태 API로 완료 여부를 확인한다.

| 메서드·경로 | 기능 |
|---|---|
| GET `/options` | 공항·주차장·입력 제약/할인 선택 정보 |
| GET `/defaults`, POST `/defaults` | 비밀번호 제외 저장 정보 |
| POST `/jobs` | 입력 검증 후 작업 생성. 1회 조회 또는 감시 모드 |
| GET `/jobs/active` | 활성 작업의 안전한 요약 또는 null. 이전 실행의 결과 확인 필요 작업도 포함 |
| GET `/jobs/<id>` | 상태, 최종 조회 결과, 검증된 예약 요약, 안전한 오류 정보 |
| PATCH `/jobs/<id>` | 결제 전 상태에서만 기존 문서 정리 후 입력 버전 갱신 |
| POST `/jobs/<id>/stop` | 결제 전 작업 중지. 결제 전송 가능성이 있는 상태에서는 409, 브라우저 유지 |
| POST `/jobs/<id>/prepare` | 실제 가능한 날짜로 정보입력 단계 준비, 공식 할인·요금 확인 |
| POST `/jobs/<id>/proceed` | 수동 진행 모드의 중복·잔여석 재조회. 자동 모드에서는 워커 내부 단계로 실행 |
| POST `/jobs/<id>/show-browser` | 유지된 공식 브라우저 창을 전면에 표시. 결제 요청 자체는 실행하지 않음 |
| POST `/jobs/<id>/reprepare` | 취소·만료·검토 상태에서 새 공식 문서로 정상 재준비 |
| POST `/jobs/<id>/resolve` | 공식 결과를 사용자가 확인한 기록과 관리 종료. 자동 RESERVED 전환 아님 |
| GET `/jobs/<id>/logs` | 단계별 마스킹 로그 |
| GET `/notifications/status` | 텔레그램 설정 여부와 마지막 발송 결과. 토큰은 제외 |
| POST `/notifications/test` | 사용자가 “테스트 알림”을 누를 때만 실제 테스트 메시지 발송 |
| POST `/jobs/<id>/notifications/resend` | 사용자 요청으로 현재 유효한 인계 알림 또는 최신 정정만 재발송 |

기본 상태는 `DRAFT → CHECKING → WAITING_AVAILABLE / AVAILABLE → PREPARING → RECHECKING → PAYMENT_CONFIRM_READY → PAYMENT_DISPATCHING → PAYMENT_IN_PROGRESS`다. RESERVED는 공식 완료 증거가 검증될 때만 사용한다. STOPPING, STOPPED, REVIEW_REQUIRED, HANDOFF_CANCELLED, HANDOFF_EXPIRED, SESSION_EXPIRED, INTERRUPTED, ERROR, PAYMENT_RESULT_UNKNOWN, PAYMENT_FAILED, CLOSED_BY_USER를 별도 관리한다. 알림 상태는 PENDING/SENDING/SENT/RETRYING/FAILED/UNKNOWN/CANCELLED이며 공통 알림 비활성 시 DISABLED로 표시한다.

입력·일시·할인 변경은 결제 전 상태에서만 허용한다. 기존 문서의 진행 차단·정리 후 입력 버전을 갱신한다. 결제 요청이 전송됐을 가능성이 생긴 이후에는 변경·재준비·새 작업을 거부한다. 요약 버전은 자체 동시성 관리용이며 공항이 발급한 승인 토큰이 아니다.

화면 진입·새로고침 때 먼저 `/jobs/active`를 조회하고 기존 작업의 상태·로그·브라우저 표시 기능에 다시 연결한다. 복구 전에 새 작업을 자동 생성하지 않는다. 자체 탭 닫힘은 작업 중지나 공식 브라우저 종료가 아니다. 비밀번호는 상태 API로 복원하지 않는다. 프로세스 재시작으로 끝난 결제 전 작업은 최근 중단 요약으로, 결과 불명 작업은 활성 작업으로 표시한다.

## 공항 연동 동작

1. 정상 시작 페이지에서 세션 생성, 공항·주차장 선택 목록 조회.
2. 사용자의 실제 입출차 날짜로 잔여석 조회. 00이면 다음 절차, 10이면 만차 상태를 표시하고 감시 모드일 때만 정해진 간격으로 다시 조회.
3. 실제 00인 날짜 그대로 resInsert.do로 진입. 입력 화면 존재, 날짜·주차장 일치, 공식 금액을 검증한다. HTTP 200에 오류 페이지가 담긴 경우도 실패로 처리한다.
4. 자체 입력값을 공식 폼에 적용. 할인은 공식 조회 결과를 반영하고 요금을 다시 읽어 자체 화면에 표시한다. 할인 연동 규격이 확인되지 않은 경우 일반만 활성화하고 할인 선택을 성공으로 가장하지 않는다.
5. 시작 시 받은 자동 진행 동의를 바탕으로 입력·약관 검증, 중복 조회, 공식 예약내용 확인 및 잔여석 재조회. 확인창 내용과 입력 일치 여부를 검사하고 정상 흐름에서만 확인한다. 중복 10/노쇼 20은 사유를 표시하고 중단한다. 마지막 잔여석 10이면 기존 준비를 폐기하며 감시 모드에서는 WAITING_AVAILABLE로 돌아가 새 문서에서 다시 준비한다.
6. 실제 최종 재조회 00, 현재 문서·입력 버전 일치, 양수의 검증된 금액과 결제 모달 표시를 함께 확인하면 PAYMENT_CONFIRM_READY와 outbox 이벤트를 같은 트랜잭션으로 기록한다. 감시를 멈추고 “결제 대기 — 예약 미완료”, 마지막 조회 시각, 자체 재확인 기준을 표시한다.
7. 브라우저를 유지하고 사용자가 해당 창에서 결제 진행 여부를 결정한다. 자동화는 결제 확인을 누르지 않는다. 사용자가 누르면 아래 전송 제어 규칙으로 첫 payment.json 요청만 허용하고 PG 전환을 관찰한다.
8. 공식 결제창의 실제 동작을 사용자가 이어받는다. 결제 준비 응답 누락/타임아웃은 자동 재전송하지 않고 결과 불명 상태로 처리한다. 알림 발송 실패를 이유로 1~7단계를 다시 실행하지 않는다.

조회 제한·접근 제한 응답은 중지하고 이유를 표시한다. 30초 기본 간격은 서비스 설계 초안이며 공항이 공지한 허용 호출 빈도로 확인된 값은 아니다.

## 상태별 브라우저 소유권과 정리

`input_version`은 입력 변경마다, `generation`은 새 공식 정보입력 문서 생성마다, `handoff_epoch`는 새 결제 대기 진입마다 증가한다. 런타임의 page 식별자를 generation에 연결한다. `job_id`, `run_id`, 상태·각 버전·조회/전이 시각·인계 기한·결제 시도 기록과 알림 식별자는 비밀정보 없이 영속화한다.

| 상태/사건 | 허용 동작과 전이 | 브라우저·활성 슬롯 |
|---|---|---|
| DRAFT / CHECKING / WAITING_AVAILABLE / AVAILABLE / PREPARING / RECHECKING | 변경·중지 가능. 먼저 STOPPING으로 전환해 이전 generation 진행을 차단 | 정리 완료 후 STOPPED 또는 새 입력의 DRAFT, 슬롯 해제 |
| PAYMENT_CONFIRM_READY에서 변경·중지 | 결제 요청과 같은 상태 잠금으로 경합 판정. 전송 허용 전일 때만 취소 | 알림 무효화·문서 전송 차단·컨텍스트 정리 후 슬롯 해제 |
| 결제 모달 취소/닫힘, 결제 전 페이지 이탈 | HANDOFF_CANCELLED | 이전 문서 재사용 금지. 정리 후 슬롯 해제 |
| 자체 인계 재확인 기한 경과 | HANDOFF_EXPIRED | 이전 문서 전송 차단·정리, 사용자 재준비 필요 |
| 결제 전 브라우저 종료/명시적 세션 오류 | SESSION_EXPIRED 또는 ERROR와 사유 기록 | 알림 무효화·정정 후 슬롯 해제 |
| REVIEW_REQUIRED / 결제 전 ERROR | 불일치·예외 원인을 표시하고 사용자 수정/재준비 대기 | 이전 문서 전송 차단·정리 후 슬롯 해제 |
| PAYMENT_DISPATCHING / PAYMENT_IN_PROGRESS | 입력 변경·stop·prepare·proceed·재준비·새 작업은 409 | 사용자 결제 중 브라우저와 슬롯 유지 |
| PAYMENT_RESULT_UNKNOWN | 자동 재전송·재예약·컨텍스트 자동 정리 금지. 공식 결과 확인 필요 | 가능한 브라우저 유지, 슬롯 점유 |
| RESERVED / 검증된 PAYMENT_FAILED | 검증 근거 기록, 완료 화면 표시 | 명시적 관리 종료 시 정리·슬롯 해제 |
| CLOSED_BY_USER | 사용자가 공식 결과를 직접 확인한 후 관리 종료 | 명시적 동의 후 정리·슬롯 해제. RESERVED로 표시하지 않음 |

STOPPING 이후 도착한 조회 응답은 후속 준비나 알림을 생성할 수 없다. 결제 전송 허용 기록이 먼저 확정됐으면 중지·입력 변경을 거부하고 브라우저를 유지한다. 취소 기록이 먼저라면 뒤따른 결제 준비 요청을 전송 전에 차단한다. 활성 슬롯은 문서 정리 완료 전에 해제하지 않는다.

모달 숨김/페이지 이탈은 결제 전 상태에서만 취소로 해석한다. 요청 전송 경계에서 PAYMENT_DISPATCHING을 먼저 기록해 결제 클릭 이후 모달 숨김·PG 전환을 취소로 오판하지 않는다. 단순 visibility 이벤트로 결제 결과를 판정하지 않는다.

`/reprepare`는 결제 전송 표시가 없고 다른 활성 작업이 없을 때만 허용한다. 취소·만료·검토·중지·세션 오류 이후에는 새 generation의 공식 문서에서 처음부터 준비한다. 같은 문서에서 payment()를 다시 실행하지 않는다. 정리된 비밀번호가 필요하면 사용자에게 재입력받는다.

결제 완료 판정이 미지원이거나 결과 불명인 경우에는 사용자가 공식 예약조회·결제 결과를 확인하고 `/resolve`에서 확인 결과와 관리 종료 동의를 기록할 수 있다. 이 기록은 자동 검증된 예약 성공과 구분하며 CLOSED_BY_USER로 처리한다. 공식 예약 취소·환불을 실행하는 기능은 아니다.

## 공식 결제 준비 요청의 1회 전송 제어

자체 API 중복 제어 외에 BrowserContext의 모든 페이지·팝업에서 공식 `/reservation/payment.json` 전송을 관측·제어한다. Service Worker 등 제어 밖 전송이 발생하지 않도록 설정하고 fixture로 검증한다. 이 경계는 정상 요청의 중복·오래된 전송만 막으며 요청값이나 서버 응답을 조작하지 않는다.

1. 실제 마지막 조회 00, 현재 PAYMENT_CONFIRM_READY, 문서/generation·입력 버전 일치, 준비 요약과 폼 날짜·주차장·금액 일치, 인계 기한 미경과일 때만 최초 요청을 허용한다.
2. 워커/SQLite 잠금 안에서 payment_attempt_id를 생성하고 `payment_may_have_been_sent=true` 및 PAYMENT_DISPATCHING을 먼저 영속화한다. 기록 실패 시 전송하지 않는다. 기록 완료 후 정상 요청을 그대로 전달한다.
3. 같은 job의 추가 payment.json 요청은 차단한다. 공식 창 더블클릭·누적 핸들러·여러 탭도 포함한다. 추가 요청 차단 때문에 이미 진행 중인 최초 요청을 취소하거나 다시 보내지 않는다.
4. 정상 응답과 PG 전환을 관측해 PAYMENT_IN_PROGRESS로 진행한다. 전송 이후 타임아웃·브라우저 종료·판별 불가능한 응답·프로세스 종료는 PAYMENT_RESULT_UNKNOWN으로 기록한다. 서버에 도착하지 않았다고 추정해 자동 재전송하지 않는다.
5. 전송 허용 기록과 실제 전송 사이에 프로세스가 종료돼도 결과 불명으로 처리한다. 서버 측 멱등성이 확인되지 않았으므로 정확히 한 번의 서버 처리나 중복 과금 방지를 보장한다고 표현하지 않는다.

사용자가 시작한 정상 PG 후속 흐름은 별도로 관측하고 임의로 재실행하거나 일괄 차단하지 않는다. 자동 진행 중 비정상·0 이하의 `paymentAmt` 또는 예상하지 않은 insertAction.do 직접 제출은 결제 전에 차단하고 REVIEW_REQUIRED로 전환한다. 이 검사를 정상 캡처에서도 음수인 `receiptAmt` 전체에 일괄 적용하지 않는다. 결제 이후 공식 완료 요청과는 상태를 구분한다. 미확인 후속 경로를 무조건 막아 정상 결제를 중간에 끊는 방식은 채택하지 않는다.

## 인계 신선도와 재준비

마지막 정상 재조회 시각 `availability_checked_at`과 자체 기한 `handoff_deadline`을 저장한다. `config/gimpo_parking.toml`의 `request.handoff_max_age_sec` 기본값은 120초다. 이는 서비스의 보수적인 재확인 정책이며 공항의 주차면 홀드·세션 만료시간이 아니다. 이 시간 이내에도 주차면을 보장하지 않는다.

대기 타이머, 결제 준비 요청 전송 직전, 알림 발송·재시도, 브라우저 표시 요청에서 기한을 검사한다. 기한이 지났으면 HANDOFF_EXPIRED로 전환하고 이전 문서 전송을 차단한 뒤 새 정상 준비를 요구한다. 프로세스 재시작 후에는 시각만 보고 인계를 복구하지 않는다.

새 문서에서 입력·금액·중복·잔여석을 다시 확인하고 실제 00이면 새 handoff_epoch로 알린다. 만차·세션 오류이면 결제 대기 알림을 만들지 않는다. 화면과 메시지에는 마지막 확인 시각 및 재확인 필요 상태를 표시한다.

## 프로세스 종료와 재시작 복구

정상 종료 요청은 새 작업을 차단하고 결제 전 작업을 정리한다. 결제 전송 가능성이 있는 작업은 종료 전에 PAYMENT_RESULT_UNKNOWN을 기록한다. 프로세스 종료가 브라우저 유지, 결제 실패 또는 예약 취소를 의미한다고 가정하지 않는다.

SQLite에는 run_id, 마지막 상태, 입력/generation/인계 회차, 결제 전송 표시, 알림 상태·message_id·정정 여부를 저장한다. 비밀번호·공항 쿠키는 복구하지 않는다. 새 프로세스는 작업을 받기 전에 단일 실행 잠금을 확보하고 이전 run을 다음처럼 정리한다.

1. 결제 전 작업은 INTERRUPTED로 종료한다. 이전 브라우저가 살아 있어도 런타임 소유권과 요청 제어가 복구되지 않으면 유효한 인계로 취급하지 않는다. 직접 실행한 결제 전 브라우저만 추적·정리하며 다른 사용자 브라우저를 종료하지 않는다.
2. 결제 전송 표시가 있는 작업은 PAYMENT_RESULT_UNKNOWN으로 보존하고 활성 슬롯을 점유한다. 남은 결제 브라우저를 재시작 정리 대상으로 자동 종료하지 않는다. 소유권 복구가 검증되지 않았으면 이를 제어하지 않고 사용자에게 공식 결과 확인을 안내한다.
3. 이전 READY 이벤트의 PENDING/RETRYING은 CANCELLED로 폐기한다. SENDING은 전달됐을 수 있으므로 UNKNOWN으로 취급한다.
4. READY가 SENT 또는 전송 결과 UNKNOWN이면 “실행 종료로 인계가 중단되었습니다. 결제 진행 여부는 공식 사이트에서 확인해주세요” 정정을 한 번 예약한다. 죽은 브라우저로 결제를 계속 안내하지 않는다.
5. 정정 키를 영속화해 재시작을 반복해도 동일 정정 이벤트를 중복 생성하지 않는다. 알림 전송 결과 자체가 불명인 경우의 중복 도착 가능성은 별도로 표시한다.

## 결제 인계와 미확인 사항

우리 서비스 도메인에서 공항의 PG HTML을 그대로 실행하는 방식은 채택하지 않는다. 출처·쿠키·팝업·콜백 URL 조건이 확인되지 않았기 때문이다. 로컬 환경에서는 처음부터 화면 표시가 가능한 브라우저 컨텍스트를 유지하고, 결제 시 그 공식 사이트 창을 사용자에게 보여주는 방식을 우선 검증한다.

원격 서버에서 사용하는 경우 서버 브라우저 창을 사용자 PC에서 볼 수 없다. URL만 열거나 서버 쿠키를 프런트엔드에 전달하는 방식으로 해결된다고 가정하지 않는다. 공식 결제 URL 인계가 지원되는지 확인하거나 공식 사이트의 사용자 브라우저에서 처음부터 이어가는 별도 연동이 필요하다. 이 경우 결제 화면 열기를 구현 완료로 선언하기 전에 설계를 확정한다.

아직 모르는 항목은 payment.json의 실제 응답, PG 폼/스크립트/리다이렉트, 결제 준비 시 예약이나 주차면 홀드가 생성되는지, 할인 자격 조회의 모든 응답, 정상 완료 신호다. 초기 연동 검증 단계에서 확인한다. 임의 날짜의 결제 준비 요청을 반복 실험하지 않고, 서버 전송 없는 요청 캡처 테스트와 실제 예약 의도가 있는 사용자의 결제 진행으로 구분해 검증한다.

## 텔레그램 알림

발송은 공식 Bot API의 sendMessage를 사용한다. 모든 서비스는 접두사 없는 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ALARM_ENABLED`(기본 false)를 공유한다. 서버의 프로젝트 루트 `.env`에서 읽되 실행 환경의 값을 우선하고, 토큰은 로그/상태 API/화면에 반환하지 않는다. 토큰이 포함된 요청 URL·오류 문자열도 마스킹한다. 개인 대화 개시 또는 채널 관리자·메시지 게시 권한 설정과 chat_id 확인 절차를 안내하고 시작 전에 설정 상태·테스트 알림 경로를 제공한다. 구현 검증에서는 실제 메시지를 보내지 않는다. 사용자 요청인 테스트 알림 또는 실행 중인 예약 작업의 유효한 알림만 발송한다.

예시 메시지:

```text
[김포공항] 결제 대기
주차장: 국내선 제2주차장 주차타워 2·3층
입차: 2026-10-03 11:00
출차: 2026-10-06 18:00
예상 주차요금: 공식 화면 확인값
예약 보증금: 공식 화면 확인값
마지막 잔여석 확인: 서울 기준 시각

실행 중인 PC의 공항 예약 브라우저에서
“결제 하시겠습니까?” 확인 후 결제를 진행해주세요.
재확인 기준을 넘겼으면 자체 서비스에서 다시 준비해주세요.
아직 예약 완료 상태는 아닙니다.
작업: GMP-작업번호 / 안내 회차
```

예시 날짜는 문구 설명용이며 실제 발송에는 해당 작업의 검증된 날짜만 사용한다. 전화번호·예약 비밀번호·쿠키·PG 토큰은 메시지에 넣지 않는다. 외부에서 접속 가능한 자체 서비스 주소가 설정된 경우에만 “진행 상황 확인” 링크를 추가한다. localhost 링크를 휴대전화에서 결제 가능한 링크로 안내하지 않는다.

알림 이벤트 키는 `(job_id, input_version, generation, handoff_epoch, event_type)`다. 결제 대기 상태와 이벤트를 같은 SQLite 트랜잭션으로 기록한다. 발송 상태와 성공 message_id를 저장해 중복 이벤트 생성을 막는다.

READY 이벤트의 최초 발송과 모든 재시도 직전에 현재 run_id, PAYMENT_CONFIRM_READY 상태, 입력 버전/generation/handoff_epoch, 브라우저·문서·모달의 생존, 인계 기한을 검사한다. 알림 워커는 브라우저 객체를 직접 조작하지 않고 소유 워커에 검증을 요청한다. 검증 응답이 없거나 오래됐으면 READY를 발송하지 않는다. 정정 이벤트는 원본 이벤트와의 관련성·최신 후속 상태 버전·정정 중복 여부를 검사하며 READY 상태나 브라우저 생존을 요구하지 않는다. 따라서 이전 run의 브라우저가 없는 재시작 정정도 발송할 수 있다.

결제 시작·모달 취소·입력 변경·중지·기한 만료·브라우저 종료 시 미발송 READY를 CANCELLED로 바꾼다. 작업별 발송 순서를 직렬화한다. 전송 직전 검사 뒤 상태가 바뀌는 경쟁은 완전히 제거할 수 없으므로, 전송 중이면 superseded를 기록하고 결과 확인 뒤 정정 이벤트를 만든다. 상태 잠금을 잡은 채 외부 응답을 기다리지 않는다.

기존 안내가 SENT면 신규 정정 메시지를 원본에 대한 답장으로 보낸다. 원본 삭제로 답장이 실패하면 일반 정정으로 한 번 전환한다. UNKNOWN이라 message_id가 없으면 작업번호를 포함한 독립 정정을 보낸다. 미전송 이벤트는 취소만 한다. 정정 키는 원본 이벤트와 후속 상태 버전으로 중복 억제한다. “결제 진행 시작/인계 취소/재확인 필요/실행 종료”처럼 관측한 사실만 알리고 확인하지 않은 결제 성공·실패를 단정하지 않는다.

### 알림 오류의 종료 조건

- 429: retry_after를 따른다. 재시도 시 인계 유효성을 다시 검사하고 기한이 지나면 READY를 취소한다.
- 명확한 일시 서버 오류: 최대 3회 간격을 늘려 알림만 재시도한다. 소진 시 FAILED로 종료한다.
- 인증·수신자 오류: FAILED로 종료하고 설정 수정·테스트 알림 경로를 표시한다.
- 전송 타임아웃/연결 종료로 도착 여부 불명: UNKNOWN으로 멈추고 READY를 자동 재전송하지 않는다. 화면에 “알림 도착 여부 불명”과 명시적 재발송 버튼을 표시한다.
- 사용자 재발송: READY는 현재 인계 유효성, 정정은 최신 후속 상태 버전을 검사한다. 같은 작업번호·새 발송 회차를 사용하고 중복 도착 가능성을 안내한다. 더블클릭은 같은 회차로 합친다. 브라우저 준비·잔여석 조회·결제 요청을 재실행하지 않는다.
- 정정 알림도 제한 재시도를 적용한다. UNKNOWN/FAILED이면 “정정 안내 미확인”을 표시하고, 수동 재발송에는 해당 정정의 최신성을 검사한다.

알림 실패만으로 브라우저를 닫지 않는다. 다만 별도의 인계 기한·취소 정책은 적용한다. 공항의 실제 세션 만료시간은 미확인이므로 서비스 재확인 기준을 공항의 예약 유효시간으로 표현하지 않는다. 주차면 확보나 메시지의 정확히 한 번 전달을 보장하지 않는다.

공식 참고: https://core.telegram.org/bots/api#sendmessage , https://core.telegram.org/bots/api#responseparameters

## 구현 순서와 검증

1. 연동 계약: 캡처를 비밀정보 없는 fixture로 정리하고 공식 모달 재진입의 요청 중복도 회귀 사례로 보존한다. 미검증 PG 이후 자동 완료 판정은 비활성화한다.
2. 런타임: reloader 없는 단일 실행, SQLite 상태·결제 시도 기록, 명령 큐, 활성 슬롯, 시작/종료·복구 규칙부터 구현한다.
3. 화면: 김포 Blueprint와 카드 연결, 입력 검증·기본값, 날짜 선택기 매개변수화, 활성 작업 재연결을 구현한다.
4. 정상 준비: 순차 조회·중지·세션 오류, 새 문서 준비, 공식 할인/금액, 중복·잔여석 재검사를 구현한다.
5. 인계: 상태별 취소, 오래된 인계의 새 문서 재준비, 결제 준비 요청 1회 제어, 사용자 브라우저 인계를 구현한다.
6. 알림: 상태와 원자적으로 생성하는 outbox, 발송 전 검증·취소·정정·UNKNOWN·재시작 복구를 구현한다.
7. 아래 수용 기준과 T2 회귀를 확인한 뒤 지원 실행·Chromium 설치·Telegram 설정·직접 결제 방법을 README에 기록한다.

외부 사이트 응답을 로컬 fixture로 재현하는 테스트가 기본이며, 테스트에서 실예약·결제 요청이 나가지 않도록 기본 차단한다. API/상태 테스트는 HTTP 200인 만차·오류 HTML을 반드시 포함한다. Playwright 테스트는 입력폼부터 결제 준비 요청 생성까지 가로채 검증하고, 비밀번호·쿠키가 저장 파일·로그·상태 응답에 없는지도 확인한다. 실제 사이트의 읽기 검증과 실제 결제 완료 검증은 별도로 기록한다.

## 리뷰 대응 수용 기준

| ID | 검증할 동작 |
|---|---|
| R1 | 공식 모달 취소→재진입, 확인 더블클릭, 누적 핸들러가 요청을 생성해도 같은 job의 payment.json 외부 전달은 최대 1회. 기존 문서 재준비 금지와 generation 확인 |
| R2 | PAYMENT_DISPATCHING/IN_PROGRESS/RESULT_UNKNOWN에서 stop·입력 수정·새 작업은 409, 기존 브라우저 유지. 중지와 최초 결제 요청 경합에서 먼저 기록된 전이만 실행 |
| R3 | 모달 취소·닫힘·결제 전 페이지 이탈은 HANDOFF_CANCELLED. 진행 차단·미발송 알림 취소·컨텍스트 정리 후 슬롯 해제. 결제 후 PG 전환을 취소로 오판하지 않음 |
| R4 | 인계 기한 경과·알림 지연·기한 직전 클릭을 검증. 오래된 문서의 전송은 없고 새 문서에서 실제 재조회. 재준비 만차·세션 만료 때 READY 안내 없음 |
| R5 | 지원 실행의 debug/reloader 비활성화, 개발용 reloader에서 실제 작업 거부, 워커 시작/종료 1회, 이전 프로세스의 준비 상태 재사용 없음 |
| R6 | 자체 화면 새로고침·탭 재개 시 `/jobs/active`로 재연결. 작업·알림 중복 생성 없음. 비밀번호는 상태 응답으로 복원하지 않음 |
| R7 | 429 대기 중 모달 취소·입력 변경·결제 시작·브라우저 종료 각각에서 오래된 READY 취소. 전송 중 상태 변경이면 결과에 따라 정정 이벤트 한 번 생성 |
| R8 | SENT 직후 강제 종료·재시작 시 READY 재발송 없이 정정 생성. 브라우저·READY 상태가 없어도 최신 정정 발송 가능. SENDING 종료는 UNKNOWN. 재시작 반복에도 같은 정정 이벤트 중복 생성 없음 |
| R9 | Telegram 타임아웃은 UNKNOWN으로 종료. 사용자 재발송은 최신 인계만 허용하며 브라우저 절차를 재실행하지 않음. 인증 오류와 정정 실패를 화면에서 구분 |
| R10 | 김포 달력 선택·직접 입력·서버 검증의 정책 일치. 45일 경계·자정·PC 시간대·10분 단위 검사와 T2 날짜 범위 회귀 |
| R11 | 0 이하/비정상 paymentAmt와 자동 단계 insertAction.do는 REVIEW_REQUIRED, 외부 예약 생성 요청 없음. 정상 음수 receiptAmt 및 결제 이후 완료 흐름과 구분 |
| R12 | 상태 전이/outbox 생성 중 장애에도 결제 대기 상태만 또는 알림만 남지 않음. 결제 시도 기록 직후 종료는 결과 불명으로 복구, 자동 재전송 없음 |
| R13 | HTTP 200 만차·오류 HTML, 중복/노쇼, 최종 재조회 만차, 할인 실패를 성공으로 표시하지 않음. 감시 모드의 최종 만차는 준비 폐기 후 정상 감시 복귀 |
| R14 | 알림 실패만으로 유효한 브라우저를 닫지 않음. 비밀번호·쿠키·PG 토큰·Telegram 토큰이 저장 파일/로그/상태 응답/알림에 없음. 중지 후 뒤늦은 응답이 새 알림을 만들지 않음 |

R1~R6은 최종 리뷰의 주요 6개 지적, R7~R9는 알림 리뷰의 세부 지적, R10은 날짜 선택기, R11은 직접 예약 생성 분기의 조건부 방어를 반영한다. R12~R14는 결합된 규칙의 경합·장애와 회귀를 확인한다.

필수 환경 변경은 Playwright 런타임과 Chromium 설치 안내다. 배포 형태 확정 후 `requirements.txt`, README의 실행·브라우저 설치·지원 범위를 갱신한다.

구현 결과와 오프라인 검증 내역은 `2026-09-27-gimpo-implementation.md`에 기록한다. 실제 사이트 전체 연동과 PG 완료 검증은 오프라인 검증과 구분한다.
